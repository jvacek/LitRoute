# i18n on the React side

The frontend uses **react-i18next** for all UI strings. Translations are bundled at build time (no HTTP backend) — webpack imports the JSON files directly.

This file covers React-side conventions. For translation **tooling** (lint hook, coverage script, lookup script, duplicate-finder, unused-key checker, Weblate integration), see `scripts/README.md`.

## Files

| Path                                                 | Purpose                                                                                                     |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `flamerelay/static/locales/en/translation.json`      | Source of truth — all English strings, nested by feature area                                               |
| `flamerelay/static/locales/<lang>/translation.json`  | Weblate targets — same shape as `en/`, values populated by translators. Currently `fr`, `nl`, `cs` on disk. |
| `flamerelay/static/js/i18n.ts`                       | i18next init + `LANGUAGES` array — only listed locales are bundled and offered in the picker                |
| `flamerelay/static/js/components/LanguagePicker.tsx` | Language selector rendered in `Navbar.tsx`                                                                  |

A locale present in `static/locales/` is **not** the same as a locale bundled into the app. `cs` lives on disk so Weblate can populate it, but it's deliberately omitted from `i18n.ts` until coverage reaches the threshold (rough rule: parity with `nl`). To ship a new locale, add the import + entry in `LANGUAGES` in `i18n.ts` — that's the toggle.

`i18n.ts` is imported once in `project.tsx` before the React render. `initReactI18next` wires i18next into the React context — no `<I18nextProvider>` is needed.

## Auto-detection

`i18next-browser-languagedetector` runs on mount. Detection order: `['localStorage', 'navigator']`. The user's choice from `LanguagePicker` is persisted to `localStorage` automatically.

## Using translations in components

```tsx
import { Trans, useTranslation } from 'react-i18next';

const { t, i18n } = useTranslation();

// Plain string
t('section.key');

// Interpolation
t('unit.status.currentlyIn', { place });

// Plural (keys: section.key_one / section.key_other)
t('unit.status.lastSeenDaysAgo', { count: days, place });

// Embedded JSX (links, <strong>, custom spans) — use <Trans>
<Trans
  i18nKey="unit.supportPrompt"
  components={{ supportLink: <Link to="/support/" className="…" /> }}
/>;

// Date locale — always use the resolved language, never hardcode 'en-GB'
date.toLocaleDateString(i18n.resolvedLanguage, { … });
```

## Non-hook contexts (helpers, event handlers)

`useTranslation()` only works inside React components. From a helper or handler outside a component, import the singleton:

```ts
import i18n from '../i18n'; // adjust relative path
i18n.t('unit.deleteConfirm');
```

Prefer moving the helper **inside** the component so it can use the `t` from `useTranslation()` — that picks up language changes reactively.

## Key naming

- Nested by feature area: `nav.*`, `footer.*`, `home.*`, `auth.*`, `unit.*`, `checkin.*`, `settings.*`, etc.
- Plurals: i18next `_one` / `_other` suffix — `unit.status.lastSeenDaysAgo_one` / `unit.status.lastSeenDaysAgo_other`.
- `<Trans>` component tags use lowercase descriptive names — `<supportLink>`, `<strong>`, `<handwriting>`.

## What needs a key

Add a key for anything a translator would need to change. **Do not** add a key for:

- Universal symbols and punctuation — `*`, `©`, `→`, `←`, `…`
- Copyright notices — hardcode as `© {new Date().getFullYear()} LitRoute` (year stays dynamic, brand name is not translated)
- Brand names used in isolation — "LitRoute" is always "LitRoute"
- Purely numeric values or codes

## Adding a new string

1. Add the key + English value to `flamerelay/static/locales/en/translation.json` under the appropriate section.
2. Use `t('your.key')` or `<Trans i18nKey="your.key" …>` in the component.
3. Weblate picks up new keys automatically and keeps the target-locale files in sync — no manual edits to non-English files.

## Coverage

Every user-facing string in the SPA goes through `t()` / `<Trans>`. If you spot a bare English literal in a component, it's a bug — wrap it with a key in the right `en/translation.json` section and Weblate will pick it up.

## JSON values use real characters, not HTML entities

The JSX rule "no bare apostrophes/quotes in JSX text" does **not** apply to `static/locales/*/translation.json`. Those values are inserted into the DOM as raw strings via `t()`, so `&apos;` would render literally as `&apos;`. Write `lighter's` in JSON, not `lighter&apos;s`.
